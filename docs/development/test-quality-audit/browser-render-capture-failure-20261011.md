# Browser acquisition error visibility (2026-10-11)

Related: #1990 and #2325. In an explicit, cache-backed, read-only `theme:yossistyle` live/reference diagnostic run on 2026-10-11, `capture-browser-rendering.mjs` emitted only `browser capture and cleanup both failed` and exited 1. The sealed request-gate snapshot in the diagnostic records reported `enforcement_failed: true`, with 15 acquisition barriers; source/local HTTP 200, DOM and screenshots were nevertheless written before terminal failure. **This result is NOT an accepted Wikidot oracle, a whole-page parity PASS, or evidence that any difference is caused by Wikijump.** The failed run was not retried or reacquired under a new cache identity; preserve cache acquisition barriers and treat its results as diagnostics only.

The CLI previously discarded both distinct exception messages by printing only the *outer* `AggregateError.message`. The internal helper correctly retains `errors[0]` and `errors[1]`, but the CLI dropped them, making capture-vs-cleanup attribution impossible from stderr even when the errors were present.

This change prints each cause under a distinct `capture:` or `cleanup:` label in CLI output, while redacting URL query strings and common credential assignment keys. It does not alter the request gate, acquisition retry rules, or error exit status. The hermetic unit test constructs both errors, checks both messages appear and checks sample tokens are absent. Do not treat this diagnostic-output fix as resolving the acquisition gate failure; the gate remains fail-closed until the actual cause is independently established.
