# Wikijump

## Start here

1. Check the current checkout, Git/GitHub state, maintained receipts, and running services before following a handoff or older plan. Verify handoff instructions against the current state.
2. For Wikidot compatibility work, read `docs/agents/compatibility/README.md`. The historical WJLab campaign has been retired. Routine compatibility work uses regression tests maintained in this repository and run without external dependencies. Do not resume the old campaign.
3. For SCP theme localization or porting, read `docs/agents/theme-lab.md` before fetching source material, creating a Theme Lab package, adapting a theme for SCP-JP, or updating an existing port. Follow its separate procedures for new ports, accepted-port maintenance, and site-baseline migration.
4. Read the relevant specification in `docs/wikidot-specifications/` before changing Wikidot behavior. That directory contains the Wikidot specifications. Direct Wikidot observations and corpus evidence with recorded provenance take precedence over local Wikijump output.
5. Complete the workflow for the branch you work on. Source changes require focused validation, a consistent commit and push, normal PR delivery, required acceptance checks, and any required standing verification or cleanup.

## Core invariants

- **Wikidot compatibility:** Reproduce independently verified Wikidot behavior, including DOM, CSS, typography, layout, responsive design, hover, pointer, keyboard and focus interactions, editing, forms, modules, page actions, time-dependent states, errors, legacy quirks, escaping, sanitization, HTTP behavior, and security-relevant output. Internal code may differ, but observable results must match Wikidot even when its behavior is outdated or nonstandard. General web best practices do not establish compatibility. These requirements do not apply to Wikijump-only audit and verification tools.
- **General behavior:** Implement rules supported by evidence instead of special-casing captured pages. If the general rule is unclear, keep the case open for investigation. Do not hardcode test fixtures or weaken verification checks.
- **Unverified behavior:** For unsupported or unverified modules and queries, reject unsupported operations, handle the input literally, or use a fallback supported by evidence. Do not add behavior just to pass a test.
- **FTML and Wikijump:** FTML handles syntax parsing and rendering primitives. Wikijump handles behavior that needs site, page, query, import, file, permission, actor, or browser runtime state. Read `docs/ftml-boundary.md` before changing code across this boundary.
- **Mirror sites:** `scp-wiki` and `scp-jp` are mirrors. Make local authoring changes in `scpaiueouiuiuiui` unless the task explicitly requires a mirror import or repair. Read `docs/local-authoring-boundary.md` before authoring or membership work.
- **Persistent data:** Preserve `wikijump-standing-postgres-data`, `wikijump-standing-files-data`, and `wikijump-standing-cache-data`. They are persistent standing volumes. Delete candidate, fixture, and inspection resources only when no running process or rollback procedure needs them. Use legacy `runtime50x-*` resources only as migration rollback inputs; do not add them to the active runtime configuration.
- **External evidence:** Read `docs/agents/compatibility/evidence.md` before collecting external evidence or running browser compatibility checks. It defines the rules for caching, replay, browser identity, mutations, and acquisition in CI.
- **Credentials:** Do not put credentials, session cookies, bearer tokens, or private actor data in source files, issues, logs, or receipts.
- **PRs and deployment:** Use a normal two-parent PR merge. Do not force-merge, use administrator privileges to merge, or push to `scpwiki/*`. For browser-visible changes, update and verify standing after merging as required by `docs/deployment/runtime-drift-policy.md`.
- **Compatibility checks:** Before submitting a PR involving compatibility scanners or rendered constructs, read `install/local/wikidot-verification/README.md` and run the applicable corpus-pinned-literal and Wikijump-identifier-leak checks.

- The user authorizes the coding agent to work in this WSL checkout and its local development runtimes. The agent may inspect local credentials, private test actors, local-only environment files, and task-owned runtime data as needed. Never commit credentials, display them in chat or logs, put them in issues, PRs, or receipts, or copy them into tracked source files.
- Before asking the user for a token, password, or access to the local environment, inspect the available repository and machine-local resources. Before reporting a credential or runtime blocker, check running containers and exposed ports, documentation and scripts, the operator environment, local-only environment files, and private task inputs and receipts. If existing tools can create an isolated local runtime or test actor, use them instead of stopping.
- Use the environment variables required by the code you run. Do not invent variable requirements and report their absence as a blocker. In particular, `WIKIJUMP_THEME_RPC_URL`, `WIKIJUMP_THEME_ADMIN_EMAIL`, and `WIKIJUMP_THEME_ADMIN_PASSWORD` are not standard project requirements unless the task's code explicitly defines them.
- Identify the active runtime before choosing an endpoint. The persistent local development environment normally serves Deepwell at `http://127.0.0.1:2747/jsonrpc` and Wikijump at `https://scpaiueouiuiuiui.wikijump.localhost:18443`. Theme Lab's Deepwell client also defaults to port 2747. Port 12747 is often used by temporary verification runtimes. Check `docker ps`, `docker port`, and the running services instead of assuming port 12747 is required.
- A local Deepwell service token may already be available in the operator shell or a local-only environment file. Theme Lab work on this workstation commonly uses `/tmp/opencode/local-dev.env` with `DEEPWELL_RPC_TOKEN`. Verify that the file and runtime are current before sourcing it. If the file is absent, obtain the token from the authorized local runtime or use an existing task-owned setup procedure. Do not print the token. Pass secrets through environment variables or private files, not command arguments or tracked artifacts.
- `scpaiueouiuiuiui` is the editable local authoring site. On this site, unauthenticated page changes through local Framerail may run as the built-in administrator (`user_id = -1`), as documented in `docs/local-authoring-boundary.md`. This does not apply to ordinary authoring on the `scp-wiki` and `scp-jp` mirrors. Read the boundary document before using this behavior.
- Deepwell tools and browser/session tools have different authentication requirements. Deepwell adapters that log in explicitly still need their configured session and actor inputs. Framerail's local authoring actor does not satisfy those requirements. Reuse existing verification and provisioning helpers and their private inputs. Scripts commonly use `DEEPWELL_RPC_TOKEN`, `WIKIDOT_VERIFY_ADMIN_EMAIL`, and `WIKIDOT_VERIFY_ADMIN_PASS`; some helpers provide development defaults. Check the script before asking the user to provide information already available locally.
- If no suitable persistent runtime exists, the agent may create a temporary local runtime, generate its service token, create test actors, pages, files, and revisions, run checks, and remove disposable resources afterward. Follow the standing-data and destructive-operation restrictions in this file. Ask the user only when required external or private access cannot be obtained or provisioned locally, or when approval is required for a destructive or out-of-repository operation.
